# 正式分支前的资源诊断准备

2026-10-27。诊断已审查和部署帮助入口，尚未提交GPU；正式四分支的资源布局尚未变更。

当前平台Job规则为GPU利用率持续3小时低于40%会回收，见`LONG_JOB_RESOURCE_POLICY.json`。实际暖身/完整验证单任务利用率低于门槛，因此不能把四个长时间独占单卡Job当作已经验证可持续的方案。两份暖身自身的时长上限小于3小时，继续完成后正常验收释放。

`shared_gpu_probe.py`只复用冻结源代码，以两个已验收R5 checkpoint分别恢复J0/J1/H0/H1；比较一张卡上依次执行和四独立进程并发执行。每臂每种方式仅20次R、20次T更新和512条验证推理。模型、优化器、scheduler、RNG以及解压后的逐样本预测必须完全一致。诊断不保存新模型、不读测试标签、不改变正式run或参数，不增加研究实验组。

GPU最多1张H100，平台0.2小时上限，进程组600秒硬超时；失败不自动重试或延长。必须等两暖身平台终态、释放、CPU验收通过，填入两份last.pt实际SHA并重新预检后才可提交。模板中的占位符不是可运行命令。

资源决策同时看真实利用率、CPU/显存、每臂吞吐和总墙钟；短时平均超过40%不能保证长期符合回收规则，正式运行仍须监测。先solo后concurrent有缓存预热偏差，所以R/T另报去掉前2步的中位数；solo时四个CUDA context仍驻留，不能冒充真实四张独立卡的测速。若改变布局，须先按实测更新整体75 GPU小时预算和预计完成时间，训练、搜索和评价协议保持不变。
