# H1 best 的验证优势为什么没有延续到测试

2026-10-28。本次仅用本地数据、保存的预测和 checkpoint 做 CPU 诊断；没有修改模型或训练代码，没有重新推理、训练或申请 GPU。原 Stage09 最终报告与验收文件保持不变。

建议：先做一次小规模的训练稳定性干预，但把后续时段的验证表现纳入验收；暂缓大范围学习率搜索和新增泛化模块。已有证据同时显示时间泛化不足和后期编码塌缩，两者不能混为同一个原因。

**一、比较口径已核对**

H0 为外层逐商品、内层四码 DiffGRM；H1 在相同架构上增加全局 Full Mixer。两组都做交替联合训练，H0 也更新基础码本。这不是 Stage07 的商品内注意力实验。

| 固定模型 | 完整验证 NDCG@5 | 完整测试 NDCG@5 |
|---|---:|---:|
| H0，R32 / T360 best | 0.008919808 | 0.008607058 |
| H1，R20 / T200 best | 0.009372056 | 0.007943674 |
| H1 相对 H0 | +5.07% | −7.71% |

四份评估的 dataset binding、指标协议、beam32、FP32、目录、seed2024 一致。主指标都评价最高分的一份五商品列表。逐样本重新按预测 ID 与五个真实目标计算 NDCG，与原结果一致。不存在这次验证用 beam32、测试用 beam256 的差异。

**二、划分确实包含时间变化，且优势在验证期末已经消失**

数据来自 KuaiRec big_matrix，以 30 分钟间隔划分人工 session，再取符合规则的连续五商品块。按全局时间切分；跨边界 session 不作为目标样本。所有已检查的验证/测试历史严格早于各自目标，session 均在对应区间内。测试使用当时已观察到的历史，属于滚动评估，不把尚未发生的目标放进历史。

| 集合 | 实际目标时间，北京时间 | 样本数 |
|---|---|---:|
| 训练 | 6月25日—8月28日18:06前 | 709,443 |
| 验证 | 8月28日18:06—8月31日21:49前 | 71,657 |
| 测试 | 8月31日21:51—9月10日，主要集中在9月1—5日 | 53,194 |

保持 H0 R32 / H1 R20 两个 best 不变，只按验证样本的目标时间中点 `8月30日07:57:21` 分段：

| 验证时段 | 样本数 | H0 NDCG@5 | H1 NDCG@5 | 相对差 |
|---|---:|---:|---:|---:|
| 前段 | 38,644 | 0.00996252 | 0.01112825 | +11.70% |
| 后段 | 33,013 | 0.00769924 | 0.00731631 | −4.97% |

逐日也有同样迹象：8月29日 H1 +11.22%，8月30日 +1.08%，8月31日的验证部分 −3.14%；测试中9月1—5日分别为 −5.20%、−11.60%、−10.63%、−2.63%、−7.04%。8月31日测试部分仅435条，H1为正，不能说每天严格单调下降。

因此，完整验证的 +5.07% 并不是一个在整个时间区间都成立的优势。它更多来自验证前段，后续时段已不占优。这里的“前后段”是数据发生的日期，不是模型训练轮次。

这是事后诊断：两段都已用于原来的 best 选择，后段不是新的独立留出集。对 R8—R35 十个分支检查点做“前段选模、后段检查”，选出的 H0 为 R23、H1 为 R20，后段 H1 仍有约 +1.26%。所以不能声称所有选模方式都会反转，也不能事后换成这个结果作为正式成绩。

**三、不能简单解释成新用户或冷商品更多**

| 固定分组的 H1 相对 H0 | 验证 | 测试 |
|---|---:|---:|
| 仅验证、测试共有的用户，按样本平均 | +4.49% | −8.36% |
| 五个目标都在训练数据中出现过 | +4.90% | −8.62% |
| 至少一个冷目标 | +7.23% | +3.92% |

冷目标定义是未出现在保留训练样本的历史与目标并集中。含冷目标样本从11.54%升到14.36%，但 H1 在该组仍有正向差值；主要负差来自已见目标组。对冷热样本比例做精确加性分解，比例变化项还略微抵消了总反转，不能把冷启动增加当成主因。

历史中的冷商品占比从3.02%升到7.09%，值得关注，但测试中没有冷历史的组 H1 也下降4.08%，有冷历史的组下降9.19%。仅靠历史冷启动也解释不完。

目标商品分布确实变化较大：训练目标中最热门的前10%商品，在验证目标中占13.85%，测试中占6.26%。然而逐商品 DCG 贡献的描述性分解显示，单纯改变共同商品的频率仍不足以解释反转；相同商品在后续样本中的相对命中和排序也发生变化。不能由此单独确定是用户偏好变化、模型过拟合还是编码与推荐器失配。

**四、H1 输出更集中，是值得继续跟踪的信号**

统计每个请求最高分的五商品列表，在整个数据集上的商品出现频率：

| 指标 | 验证 H0 / H1 | 测试 H0 / H1 |
|---|---:|---:|
| 实际推荐过的不同商品数 | 815 / 690 | 771 / 613 |
| 最常被推荐的10件商品占所有推荐位置的比例 | 28.02% / 39.01% | 29.78% / 45.23% |

例如内部商品7821，验证目标出现166次，测试目标未出现；测试中 H0 仍推荐9,480次，H1推荐15,420次。这里“未出现”仅指本次保留的测试目标，不代表商品下架或所有用户都不喜欢它，更不能用测试标签将它从候选目录删除。

这说明 H1 的首选列表更偏向少数商品，且这种集中在后续时段更明显。它与时间泛化不足相符，但还不是致因证明，也不等于 R35 的码本塌缩。此处是全体请求的推荐频率，不是每个请求聚合候选的 coverage@50；两者不能混用。

**五、训练不稳定是真问题，但不能直接解释 R20 的测试反转**

已有 checkpoint 与独立选码复核：H1 R20 有9,600种 SID，碰撞商品占12.91%；R35只剩2,551种 SID，碰撞商品占91.41%。交互修正/基础码本整体范数比从0.824升到4.230。与此同时，R学习率持续衰减，T阶段 Mixer 学习率仍固定1e-4。这支持检查后期编码更新，但尚未证明某个学习率设置就是唯一原因。

测试加载的是 **R20**，后来的 R35 权重不会倒过来污染 R20。并且在 H1 R20 编码下，目标发生 SID 碰撞的比例从验证5.79%降到测试5.06%；只看无碰撞目标的样本，H1仍从验证 +9.22% 变为测试 −6.24%。测试碰撞更多也不是答案。

还有一个值得保留的可能性：同在 R20，H1 的后段验证比 H0 R20 高4.39%；但 H0 后续训练到 R32 后超过了 H1 R20。稳定训练可能给 H1 留出继续适应的机会，是否有效必须做干预实验，不能当成已成立的解释。

样本平均的验证差值，按用户聚类 bootstrap 95%区间为 `[+0.0000507, +0.0008519]`；测试为 `[−0.0011025, −0.0002366]`。用户等权平均时两者区间均跨零。这些区间固定了已有 checkpoint，不包含选 best 的不确定性；也只有一个训练 seed，不能声称跨用户、跨 seed 的稳定收益已经成立。

**六、下一步：先做最小稳定性干预，用时间泛化判断是否值得继续**

不建议直接扩展为大规模学习率搜索，也不建议马上增加 dropout、去热门偏置或其他新损失。当前最清楚、最容易隔离的干预仍是停止后续编码更新。把此前三支方案缩成两支：

| 分支 | 从相同 H1 R20 状态开始，到 R26 | 用途 |
|---|---|---|
| A | 保持原来的40T＋3R交替设置 | 原轨迹对照；只有恢复/配置/随机流核对一致时才复用原R23/R26结果 |
| B | 固定基础码本、Mixer和SID，只继续6R | 保留已学到的交互，检查推荐器能否在稳定编码下继续改善 |

B 不关闭 Mixer；继承推荐器、优化器和原35R学习率时钟。保持原R阶段编号、训练样本顺序和随机流对应，不因跳过T而改变这些因素。A的T更新200→280，B保持200，这是有意干预。新分支需明确分叉记录，不伪改原checkpoint绑定。

提前固定 R26 为判断终点，R23仅观察，不再挑新峰值。仍以完整验证单列表 NDCG@5 为主指标，同时固定报告上述前/后段、用户等权结果、输出集中度和SID诊断；当前测试不参与分支选择。不能仅用“优于已经塌缩的A”作为成功标准：

- B相对A止跌，但没有改善自己的R20或后段仍低于H0：只能说训练稳定性改善，交互的泛化收益仍未解决，暂停扩大LR搜索。
- B同时改善完整验证和后段，且缩小与H0的后段差距：值得进入额外seed与额外时间窗口验证。
- 编码固定后推荐效果仍继续下降：后续优先检查表示偏置/推荐目标/数据时效问题，不能继续把一切归因于SID漂移。

H0 R26和既有H0 best R32均作为参考，正式比较时需给予H0相当的调参机会。更多独立验证可从原训练期内部预先划定前后时间窗口，重新训练时仅使用该窗口之前的反馈，重做对应训练依赖资产；现有checkpoint已经见过该段训练数据，不能直接拿来伪装新验证。多seed检验优化随机性，额外时间窗口检验时段敏感性，二者解决不同问题。当前测试已经用于事后诊断，后续复用时必须说明，不能再称完全未见测试。

这个稳定性干预有方法依据：ETEGRec §3.4 在交替优化后固定已收敛的Tokenizer，再训练推荐器。不过本项目尚不能认定R20编码已收敛，因此这里只把冻结作为机制检验。[ETEGRec](https://arxiv.org/html/2409.05546v3#S3.SS4)

保留全局时间切分、增加时段检查也有研究依据；不同划分及验证构造会改变模型排序，不能为了结果一致把未来数据打乱到训练中。[Time to Split，RecSys 2025](https://arxiv.org/html/2507.16289v1)
