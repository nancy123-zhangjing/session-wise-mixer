## CPU复现与候选修复

[首轮复现](OCN_AUTOCAST_CPU_DIAGNOSIS.json)对锁定原版39e94e6和新增局部模块各检查float32、BF16缓存开启、BF16缓存关闭。两版都只在BF16缓存开启时出现相同Decoder缺梯度；关闭缓存后恢复。

[四层复验](OCN_TEACHER_FIX_CPU_VERIFICATION.json)只在内存中的源码副本修改OCN teacher打分上下文，未修改实际执行源码：

| 合成模型 | 原BF16路径缺梯度张量 | teacher打分禁用缓存后 |
| --- | ---: | ---: |
| 锁定原版，4层Decoder | 40 | 0 |
| 商品内交互，4层Decoder | 40 | 0 |

两个版本各自修复前后的首次前向loss完全相同；修复后全部参数有有限梯度。候选修改仅在`score_with_mask`的`no_grad`打分中禁用autocast权重缓存，继承外层设备、精度与启用状态。当前推断是：teacher先缓存了不带梯度的权重cast，随后训练复用了该缓存。缓存开关及位置修复的CPU对照支持这个解释。

[原版候选补丁](proposed_pinned_baseline_ocn_cache_fix.patch)和[交互版候选补丁](proposed_item_local_ocn_cache_fix.patch)均**未应用**。这不是完整数据训练，也不是H100修复验收；后续真实batch的梯度覆盖、参数更新及恢复仍需GPU检查。

## 对本轮结论的影响

- 问题在锁定原版源码也可复现，不能归因于新增局部注意力或断点损坏。
- 03历史真实runtime源码和完整优化器状态未知，不能断言其正式训练一定有同一问题，也不能据此声称旧分数与当前训练严格可比。
- 直接修复后从84轮接着跑，会混合两种训练行为，不能用来检验“完整正常训练时局部交互是否有效”。若要修复后验证该问题，需要同一修复实现下的原版与交互组，重新确定预算；不自动追加这些训练。
