# DIGER SID 一致性诊断

本次检查发现：**当前 Tokenizer phase 的噪声会大幅改变临时 SID，但已保存最佳模型的确定性 SID 变化很小。下一步应优先检查推荐梯度是否在优化正式推理实际使用的编码，而不是直接扩大训练或更换交互模块。** 这不是对“联合训练无效”或“噪声导致性能下降”的因果证明。

**2026-10-12 补充边界：** 后续代码复核发现，旧 guided 打分可能将 Tokenizer 切成 eval，导致后续 batch 实际跳过噪声。下表是固定快照上显式加噪的采样结果，并未核验历史每批的真实加噪次数；`noise_scale` 日志不能替代该核验。因此不能凭本表把历史性能问题归因于“大量随机 SID”。[新短对照入口](../../pilots/noise_update/README.md) 已增加每批模式恢复和加噪调用计数，旧证据不改写。

## 检查的目的和范围

区分两个容易混淆的问题：

1. 参数不变，加入 Gumbel 噪声后，同一个商品会不会被编码成另一组 SID？这测的是**临时编码稳定性**。
2. 参数更新后，去掉噪声，商品的正式 SID 相比离线初始化究竟改了多少？这测的是**更新留下的编码变化**。

在已有 CPU 开发机上检查全部 12,101 个商品、4 位 SID、每位 256 个码字；每个带噪声条件对每个商品采样 32 次，另统计 16 对独立采样。没有训练模型、更新权重或新增 HR/NDCG 评估。

保存的 `*_joint_*` 数组属于**验证集选出的最佳 checkpoint**，不是最后一轮训练状态。Cross v1 的最佳点已经完成 2 个 Tokenizer phase；Joint Refined 完成 4 个；Cross v2 最佳点完成 0 个。

## 带噪声的临时 SID 很不稳定

“单位置不同”表示某一位码字与该商品的无噪声最近邻编码不同；“完整 SID 不同”表示四位中至少一位不同。下面是按商品目录均匀统计的采样比例，不是按训练出现频次加权的比例，也不是推荐预测错误率。

| 固定码本及采样条件 | 噪声强度 | 单位置不同 | 完整 SID 不同 | 两次独立采样的完整 SID 不同 |
|---|---:|---:|---:|---:|
| Cross v1 最佳码本，使用快照对应噪声 | 0.9045 | 95.83% | 100.0000%* | 100.0000%* |
| Cross v2 最佳码本，模拟首次 Tokenizer phase | 1.0000 | 96.67% | 100.0000%* | 100.0000%* |
| 同一 Cross v2 码本，仅降低噪声作诊断 | 0.2000 | 47.52% | 93.23% | 97.68% |
| Joint Refined 最佳码本，使用快照对应噪声 | 0.7236 | 93.09% | 99.9997% | 100.0000%* |

\* 有限采样中没有观察到完整 SID 一致，不意味着理论一致概率严格为零。理想 Gumbel 的概率计算也支持“几乎不一致”，具体精度保存在原始 JSON。

Cross v2 的噪声 1.0 是在最佳点码本上模拟**即将开始**的 Tokenizer phase，不能写成“最佳点已经使用噪声训练”。0.2 则是同一码本的反事实检查，不是重新训练后的结果。

四个位置都有这个现象，并非某一位异常：Cross v2 在噪声 1.0 下，SID0–SID3 的不同率分别为 96.69%、96.52%、96.67%、96.79%。噪声降到 0.2 后分别为 47.98%、47.05%、47.65%、47.41%。

**含义：目前噪声不是对少数边界商品做轻微探索。** 在这些快照上，Tokenizer phase 使用的编码与正式推理编码存在很大差异。代码还会分别为 history 和 target 调用采样，因此同一商品跨两个独立调用的编码也可能不一致；同一次调用内的重复商品会复用采样。

所有无噪声对照均与已保存 SID 完全一致，五份快照的 CPU 最近邻重算也全部一致，排除了本次统计中商品顺序、距离实现或读取错快照的问题。

## 更新实际留下的 SID 变化很小

以下变化均相对于**各自离线初始化**累计统计，不是训练 CSV 中“相对上一 Tokenizer phase”的变化率。

| 最佳模型 | 已完成 Tokenizer phase | 完整 SID 改变的商品数 | 商品变化率 | SID 位变化率 | 有变化商品出现在验证历史或目标中的样本 |
|---|---:|---:|---:|---:|---:|
| Cross v1 | 2 | 43 / 12,101 | 0.3553% | 0.0888% | 430 / 22,363，1.9228% |
| Cross v2 | 0 | 0 / 12,101 | 0.0000% | 0.0000% | 0 / 22,363 |
| Joint Refined | 4 | 13 / 12,101 | 0.1074% | 0.0269% | 107 / 22,363，0.4785% |

Cross v1 的 43 个商品各改变一位，SID0–SID3 分别为 9、13、10、11 个；Joint Refined 分别为 5、5、1、2 个。连续有效码本的相对 RMS 变化分别为 1.4755%、0.1996%，说明参数确实动了，但大部分商品没有跨过最近邻分配边界。

验证目标直接变化的样本更少：Cross v1 为 49 个，0.2191%；Joint Refined 为 20 个，0.0894%。验证历史含变化商品的样本分别为 382、87 个。按照原验证协议，目标为原用户序列倒数第二个商品，历史为此前最近 50 个商品，分母核对为 22,363。

这些覆盖率仅说明**输入和标签直接接触到多少编码变化**，不是可能受影响推荐结果的上限；合法候选图和后续推荐模型更新也可能影响其他样本。它也不能证明那 43 或 13 个编码变化是有益的。

## 目前可以得到什么判断

1. **需要优先检查噪声与正式编码的对齐。** “带噪声编码变化很大”与“更新留下的新编码很少”同时存在，说明不能把随机变化当成 Tokenizer 学到了新表征。噪声造成训练收益不理想是待验证解释，而非已经确认的原因。
2. **Cross v2 的最佳推荐结果仍不能归因于 Tokenizer 更新。** 新统计确认其有效码本、确定性 SID 均与初始状态相同。
3. **Cross v1 和 Joint Refined 的更新确实改变了正式编码，但作用范围较小。** 这为继续研究提供线索，不足以证明交互模块或推荐梯度带来了收益。Cross 与 Refined 的初始化不同，不能直接用两者变化大小证明 mixer 更有效。

## 建议下一步实验

先做短的**无 Gumbel 噪声、保留软反向梯度**对照。去掉前向噪声不等于断开梯度：仍可用确定性的最近邻 one-hot 做前向，用软分配做反向。

从同一个 Cross v2 第 5 个 Decoder epoch 的 checkpoint 和相同码本出发，固定推荐训练预算、数据顺序、损失权重、学习率与软反向温度，对照三条路径：

| 路径 | 操作 | 回答的问题 |
|---|---|---|
| A | Tokenizer 不更新，只继续训练推荐模型 | 继续训练本身能带来多少变化 |
| B | 无噪声更新一次完整 Tokenizer phase，再冻结并训练推荐模型 | 对齐正式编码的梯度更新是否有用 |
| C | 按当前带噪声方案更新同样一次 phase，再冻结并训练推荐模型 | 前向噪声是否影响更新的有效性 |

Tokenizer phase 使用当前 96 batch、6 次 optimizer update，随后统一观察 3 个 Decoder epoch 的恢复过程，不把其他超参数一起改掉。同步记录确定性 SID 变化、验证覆盖和验证指标；保持独立随机流，避免 Gumbel 采样消耗随机数使后续训练顺序失配。

这里是实验建议，**尚未运行**。没有完整 optimizer/RNG 状态的历史 checkpoint 启动新配对试验时，应明确这是新 pilot，不宣称精确续训。若无噪声更新出现有意义信号，再加“推荐损失权重为 0”的对照，区分收益来自推荐反馈还是重构微调；最后才做共享初始化的 mixer 消融。
